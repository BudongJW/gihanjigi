# 배포

기한지기 시제품은 Cloudflare Pages 에 올린다(의뢰인 결정, 2026-10-09). 배포는 건마다 의뢰인 승인을 받고, 승인받은
사람이 GitHub Actions 의 `deploy` 워크플로를 손으로 돌릴 때만 일어난다.

## 무엇을 올리나

- `src/` 를 빌드 없이 그대로 올린다(`wrangler pages deploy src`). 화면과 계산 엔진은 의존성이 없어서 설치와 빌드
  단계가 없다.
- `src/_headers` 가 모든 주소에 보안 헤더 넷을 붙인다. 이 파일은 Cloudflare Pages 가 설정으로 읽고, 파일 내용은
  공개하지 않는다.

| 헤더 | 값 | 까닭 |
|---|---|---|
| Content-Security-Policy | `frame-ancestors 'none'` | 다른 사이트가 시제품을 틀 안에 넣어 속이지 못하게 한다. 페이지의 CSP 메타 태그로는 이 지시를 걸 수 없다 |
| X-Content-Type-Options | `nosniff` | 브라우저가 파일 형식을 짐작하지 않게 한다 |
| Referrer-Policy | `no-referrer` | 근거 조문 링크를 누를 때 시제품 주소를 넘기지 않는다 |
| Permissions-Policy | `camera=(), microphone=(), geolocation=()` | 쓰지 않는 기기 권한을 막는다 |
| Content-Security-Policy(`/vendor/tesseract/*` 만) | `default-src 'none'; script-src 'self' 'wasm-unsafe-eval'; connect-src 'self'` | 사진 속 글자 인식 일꾼은 페이지의 CSP 메타 태그를 따르지 않으므로, 같은 주소의 모델 파일만 받고 다른 주소로는 보내지 못하게 한다 |

- 페이지의 CSP 메타 태그(`connect-src 'none'`, `form-action 'none'`)와 `noindex` 메타 태그는 그대로 둔다. 헤더의
  CSP 는 메타 태그의 정책에 더해진다.
- Pages 프로젝트를 Git 저장소에 연결하지 않고 파일을 직접 올린다(Direct Upload). 저장소를 연결하면 푸시와 PR 마다
  저절로 배포되므로 연결하지 않는다.
- 정적 파일 요청은 무료이고 개수 제한이 없다. Pages Functions(`functions/` 폴더나 `_worker.js`)를 두지 않으므로
  같은 계정의 Workers 무료 요청 한도를 쓰지 않는다.
- 2026-10-09에 wrangler 4.138.0 의 `wrangler pages dev src` 로 로컬에서 Pages 와 같은 방식으로 띄워 확인했다.
  모든 파일에 헤더 넷이 붙었고, `.mjs` 는 `application/javascript` 로 나갔으며, `_headers` 의 내용은 나가지
  않았다. 같은 서버에 `scripts/browser-check.mjs` 를 겨눠 화면 점검도 통과했다.

## 처음 한 번 할 일

계정과 토큰을 다루는 일이라 의뢰인이 직접 한다. 의뢰인이 2026-10-09에 1~4를 마쳤다.

1. 기한지기만 쓰는 Cloudflare 계정을 새로 만든다(의뢰인 결정, 2026-10-09). 다른 서비스의 Workers, 배포, 사용량과
   섞이지 않는다. 주소는 `pages.dev` 아래에 생기므로 도메인이나 DNS 는 따로 설정하지 않는다.
2. Cloudflare 대시보드의 My Profile > API Tokens 에서 Custom token 을 만든다. 권한은 Account, Cloudflare Pages,
   Edit 하나만 주고, 계정 범위는 그 계정 하나로 하고, 만료일을 둔다.
3. 대시보드의 계정 홈이나 Workers & Pages 화면에서 Account ID 를 복사한다. Account ID 는 영문 소문자와 숫자로 된
   32자이고, 대시보드 주소 `dash.cloudflare.com/<Account ID>/...` 에도 들어 있다. 계정 이메일이 아니다. 이메일이나
   빈칸이 섞이면 wrangler 가 「Invalid account ID」로 멈춘다(2026-10-11 첫 실행이 이렇게 멈췄다).
4. GitHub 저장소의 Settings > Secrets and variables > Actions 에 시크릿 둘을 넣는다.

   | 이름 | 값 |
   |---|---|
   | `CLOUDFLARE_API_TOKEN` | 2에서 만든 토큰 |
   | `CLOUDFLARE_ACCOUNT_ID` | 3에서 복사한 Account ID |

토큰은 채팅이나 커밋에 붙이지 않고 GitHub 시크릿에만 넣는다. 이 저장소는 공개 저장소지만 시크릿은 공개되지 않는다.

## 배포할 때

1. 의뢰인 승인을 받는다.
2. GitHub 의 Actions > deploy > Run workflow 에서 `main` 을 고른다. 「Pages 프로젝트를 처음 만들 때만 켠다」는
   첫 배포에만 켰다. `gihanjigi` 프로젝트는 2026-10-11 에 만들었으므로 이제 켜지 않는다(켜면 이미 있다는 오류로
   멈출 수 있다).
3. 워크플로는 시크릿이 있는지와 Account ID 에 쓸 수 없는 글자(wrangler 와 같은 기준, 영문자, 숫자, `-`, `_` 만)가 없는지
   보고, `npm run verify` 를 통과한 뒤에만 올린다. 이번 배포에 붙은 주소는 실행 요약에
   남는다.
4. production 주소 https://gihanjigi.pages.dev 를 열어 본다. 화면이 뜨는지, 브라우저 콘솔에 오류가 없는지, 기한
   화면의 근거 링크가 국가법령정보센터로 가는지 본다. `?today=2026-10-09` 를 붙이면 기준일을 고정해서 볼 수 있다.
   배포마다 붙는 주소(`<글자>.gihanjigi.pages.dev`)는 인증서가 붙기까지 몇 분 동안 TLS 오류가 날 수 있다.
5. 아래 배포 기록에 한 줄을 더한다.

2026-10-11 첫 배포에서 production 주소 https://gihanjigi.pages.dev 로 확인한 것은 다음과 같다.

- 모든 파일에 헤더 넷이 붙었다. `.mjs` 는 `application/javascript`, `.css` 는 `text/css` 로 나갔다.
- `/_headers` 를 요청하면 파일 내용이 아니라 첫 화면이 나온다.
- 배포마다 붙는 주소에는 Cloudflare 가 `X-Robots-Tag: noindex` 를 더 붙인다.
- 예시 사건(대출 사기)을 불러온 기한 화면에서 콘솔 오류가 없었고, 근거 링크는 `www.law.go.kr` 로 가서 열렸다.
- `scripts/serve.mjs` 를 배포 주소를 돌려주는 대역으로 바꾼 복사본으로 `scripts/browser-check.mjs` 를 돌려
  「화면 점검 통과: 휴대폰 320px, 390px, PC 1280px」를 받았다. 대역은 저장소에 넣지 않았다.

같은 날 두 번째 배포(41c9317)에서는 다음을 확인했다.

- 헤더 넷과 `.mjs` 형식은 첫 배포와 같다. production 주소의 `engine/deadlines.mjs` 가 새 판이다.
- 같은 대역으로 새 판의 `scripts/browser-check.mjs` 를 돌려 화면 점검을 통과했다(통지서 날짜 칸 흐름 포함).
- 개편 직후에 받은 불송치 통지에 「불송치 통지서에 적힌 날짜」 칸과 받은 날 안내가 나오고, 통지서 날짜를 개편
  전으로 넣으면 기한 없음으로 바뀌었다. 콘솔 오류가 없었고, 새 근거 링크(부칙 제7조의 개정판, 경찰수사규칙
  제97조)도 국가법령정보센터에서 열렸다.
- 이미 연 탭은 주소의 `#` 뒤만 바뀌면 다시 읽지 않으므로, 배포 뒤에는 새로 고침해서 본다.

## 되돌리기

Cloudflare 대시보드의 Workers & Pages > gihanjigi > Deployments 에서 이전 배포를 골라 되돌린다(Rollback).
되돌리는 것도 배포라서 의뢰인 승인을 받는다.

## 워크플로가 쓰는 액션

`actions/checkout@v7` 과 `actions/setup-node@v7` 을 쓴다(2026-10-11). v4 는 Node 20 으로 돌아서 러너가 Node 20 지원 종료
경고를 냈고(GitHub changelog 2025-09-19), v5 부터 Node 24 로 돈다. setup-node v5 와 v6 은 자동 캐시를 바꿨지만 이
워크플로는 `cache: npm` 을 직접 적어서 영향이 없다. 근거는 각 저장소의 릴리스 노트와 그 태그의 `action.yml`(`using: node24`)이다.
